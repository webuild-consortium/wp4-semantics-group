# Authorised Signatories application profile

Status: draft for joint review. Profile ID: `authorised-signatories`. Shape namespace: `https://w3id.org/ebwv/profile/authorised-signatories#`.

[shapes.ttl](shapes.ttl) validates the structure shown in the [Authorised Signatories PlantUML diagram](AuthorisedSignatories.PlantUML), which describes an attestation for one legal entity and one or more authorised persons. The initial README identified an attestation Turtle file, the diagram and a possible SHACL mapping as deliverables. This draft checks RDF data against the profile. A transformation from an external attestation format requires a separate mapping.

## Source and model alignment

The diagram is the source for the fields, links and multiplicities below. Its `*` marker is treated as required and `+` as optional. An attribute marker alone gives no explicit maximum. Use-case rules stay in this profile. The [joint central ontology](../../model/webuild.ttl) is the authoritative RDF source for the semantic model extension. It declares three `ebwsm:` definition annotations, an augmentation of `ebwv:Agent` under `dcterms:Agent`, the general `ebwsm:Role` and `ebwsm:RoleFulfillment` classes, and the reused `dcterms:PeriodOfTime` interval class. Agent provides a general actor category; the placement of this profile's more specific classes remains open. The profile does not yet reference these general classes; its candidate SignatoryRole has not been declared a subclass of Role, and its constraints are unchanged. The central temporal pattern does not add a fulfilment-period requirement to this profile. The table distinguishes ten existing terms from the [pinned EBWV vocabulary](https://github.com/webuild-consortium/wp4-semantics-group/blob/c34c0f810c1ba4155360a36c590c81f0ccd41c43/docs/ebwv/vocabulary.ttl), using `https://w3id.org/ebwv#` (`ebwv:`), from 25 candidate extension terms using `https://w3id.org/ebwv/semantic-model#` (`ebwsm:`). The local generated EBWV copy is older than this pinned revision. The candidate IRIs were migrated consistently in the shapes and six examples on 20 November 2026; their constraints and candidate status are preserved. The profile shapes and examples are RDF sources for the extension and are not generated from vocabulary YAML. Joint review is needed before adopting the candidates or using the profile for interoperability.

Code entries are RDF resources. The draft uses `skos:notation` for one string code and `skos:prefLabel` for the name. Citizenship, birthplace country and issuing country use the diagram's three-letter format. The existing EBWV `citizenship` property instead expects a literal and uses an alpha-2-based datatype. The proposed `ebwsm:hasCitizenshipCountry` preserves the diagram's link to a code entry. Country and LEI checks cover lexical format. Checking country code membership, LEI check digits or registry status would require separate rules and reference data. [ISO 3166 glossary](https://www.iso.org/glossary-for-iso-3166.html) · [GLEIF LEI data dictionary](https://www.gleif.org/en/lei-data/access-and-use-lei-data/gleif-data-dictionary)

The [source ownership decision](../../PROTEGE_GITHUB.md#source-ownership-and-ebwv-reuse) records why full upstream import is pending. Existing EBWV axioms must be reviewed before enabling that import; validating the examples below does not certify the imported vocabulary.

## Open decisions

- **Identifying document and region.** The attribute lists mark both links optional. The lines show a target multiplicity of one. The draft uses zero or one, pending review.
- **Signatory list.** The draft reads the list directly from the attestation, based on the explicit `1..n` link. The legal entity also lists a required `hasAuthorisedPersons` field without a separate association. Confirm whether the two paths are intended to coexist and how they would relate. Reverse multiplicities are outside the forward validation of an attestation and its linked data.
- **Legal entity and legal form.** Confirm the diagram's separate legal entity and legal person records and the use of the existing EBWV concepts for both. The diagram leaves the legal form value type open. The draft uses the string representation from the selected EBWV term.
- **Code lists and joint representation.** The diagram leaves the accepted region and document type lists open. The draft checks that these entries contain a code and a name. It checks `SOLE` or `JOINT` on each role. It leaves open how a signing group is identified and how the required combination of signers is determined.
- **Rulebook and use-case ID.** The diagram refers to a rulebook without a version or clause reference. Confirm the authoritative rulebook and project use-case ID before treating this as a normative profile.

## Example validation

Supply an attestation node typed `ebwsm:AuthorizedSignatories` and the linked records in the RDF graph. pySHACL starts from that class and follows the declared links. A graph without a target can conform without evaluating an attestation. The fixtures use synthetic data and provide the required types directly so validation works without additional inference.

| File | Expected result |
| --- | --- |
| [minimum.ttl](examples/valid/minimum.ttl) | Conforms with one signatory, a `SOLE` representation code and the optional fields omitted. |
| [joint-with-document.ttl](examples/valid/joint-with-document.ttl) | Conforms with two signatories and a `JOINT` representation code. One signatory supplies an identifying document and a birthplace region. |
| [missing-authorized-person.ttl](examples/invalid/missing-authorized-person.ttl) | Fails because the attestation has no authorised person. |

| [document-without-expiry-date.ttl](examples/invalid/document-without-expiry-date.ttl) | Fails because a supplied identifying document lacks its expiry date. |
